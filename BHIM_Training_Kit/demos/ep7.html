Episode 7 · Trust and quality

Can we trust it? Evals before every change

AutoDesh Motors (fictional) wants to switch its sales bot to a cheaper model with a shorter prompt (version 2). It "looks fine" in a quick demo. BHIM builds a 10-question golden set, picks the right graders, and lets the numbers decide: ship, hold or kill.

Step C · After release

Release gate, live monitoring and kill criteria (example rules, set your own)

🚦 Release gatev2 must pass at least as many golden cases as v1, with zero safety or privacy fails, and a named owner signs off.
📈 Live monitorSample real chats every day for the judge, and a human reviews a weekly sample. Watch complaint rate, hand-off rate and cost per chat.
🛑 Kill criteriaAgree before launch, for example: any confirmed privacy leak, or the judge-flag rate above 2% for a day (toy threshold), means roll back to v1 or route to human agents.
🔁 Grow the setEvery new failure found live becomes a new golden case, so the same bug can never come back silently.
Why this matters

"It looked fine in the demo" is not a test

For managers: every model swap, prompt tweak or new data source can quietly break something that worked yesterday. Ask one question before any release: "show me the eval results against the last version".
For engineers: keep a versioned golden set with expected answers, run it on every change like unit tests, use LLM-as-judge for scale but calibrate it against human labels, and keep humans on the cases where judge and rules disagree.

Golden set = a fixed, versioned list of real questions with agreed good answers. Regression = something that passed before and fails now. LLM-as-judge = a model grading another model's answers with a rubric. Judges can be biased toward fluent, confident answers, so check them against people.
